## 1) Cloud-first (минимум DevOps, быстрый пилот)

Когда: надо показать ценность за 1–2 недели, нет требований к полной изоляции данных.

* LLM: OpenAI GPT-4o (+ опционально YandexGPT для RU-тональности).
* Эмбеддинги: OpenAI text-embedding-3-large (или small для экономии).
* Векторка: ChromaDB (как сервис в EKS) или сразу Pinecone (Managed).
* Переранкер: cross-encoder (open-source) на CPU, либо пропустить.
* Интеграции: коннекторы GitHub/Confluence/Google Drive/Zendesk, воркфлоу в GitHub Actions/Argo Workflows.
* ingestion/indexer: 4 vCPU, 16–32 GB RAM, 200 GB NVMe (EBS gp3).
* chroma (если не Pinecone): 4 vCPU, 16–32 GB RAM, 200 GB NVMe.

Плюсы: предсказуемая скорость и качество, минимум поддержки, быстрый старт.
Минусы: токены стоят денег; контекст уходит в облако; завязка на внешние SLA.

## 2) Hybrid (рекомендовано для QuantumForge) — локальные эмбеддинги + облачный LLM

Когда: нужен контроль над данными + лучшая цена на объёмах, но хотим топ-качество генерации.

* LLM: OpenAI GPT-4o (или микс с YandexGPT для русских запросов/стиля).
* Эмбеддинги: локальные Sentence-Transformers (bge-m3 / e5-mistral-large) → быстрые и дешёвые.
* Векторка: FAISS (индекс в сервисе) + метаданные в RDS/Postgres (ваш уже есть) — просто и очень быстро.
* Переранкер: bge-reranker-large (локально, на той же GPU).
* Интеграции: коннекторы к GitHub/Confluence/GDrive/Zendesk; планировщик — Argo Workflows.
* Серверы (реалистично под ваш объём ~150–250k чанков):
* embeddings + rerank (GPU): 1× NVIDIA L4 24 GB (или A10G 24 GB)
* 8–16 vCPU, 64 GB RAM, NVMe 500 GB.
* Позволит: ~2–5 тыс. предложений/сек эмбеддингов (батчинг), быстрый переранк 10–50 кандидатов.
* faiss + api (CPU): 8–16 vCPU, 64 GB RAM, NVMe 1 TB.
* Хранение: 150–300k векторов @768–1024 dim ≈ 0.5–1.2 GB + оверхед.
* ingestion (CPU): 8 vCPU, 32 GB RAM, NVMe 500 GB (парсинг PDF/MDX, разбиение, OCR при необходимости).

Плюсы:
Эмбеддинги и векторный поиск — внутри контура (SOC2-дружелюбно).
Стоимость предсказуемая (одна умеренная GPU для всего пайплайна).
Качество поиска высокое: локальные S-T + локальный переранкер.
Быстро, просто, без тяжёлой БД: FAISS + RDS (метаданные/ACL/фильтры).

Минусы:
Готовые «кнопочные» дашборды у Chroma отсутствуют (но вы и так в Grafana/ClickHouse сильны).
Всё же зависимость от облачного LLM для ответа (контекст отправляем наружу — но без исходных данных).

## 3) Full self-hosted (макс. приватность) — локальные эмбеддинги + локальный LLM

Когда: жёсткая изоляция, запрет на вынос контекста, внутренние регламенты/аудиты.

* LLM: Llama-3-8B-Instruct / Mistral-7B-Instruct (через vLLM), 4-бит квантизация.
* Для уровня GPT-4 потребуется 70B-класс → несоразмерно дороже.
* Эмбеддинги: локальные S-T (bge-m3 / e5-mistral-large).
* Векторка: ChromaDB (как отдельная БД) или FAISS+RDS (как в варианте #2).
* Переранкер: локальный (bge-reranker-large).
* Серверы (минимум):
* llm inference (GPU): 1× L4 24 GB (7–8B в 4-битах пойдёт с приличной скоростью TGI/vLLM).
* 16 vCPU, 64–96 GB RAM, NVMe 1 TB.
* embeddings + rerank (GPU): можно совместить с LLM на одной L4, но лучше вторая L4, чтобы не мешать latency.
* vector/index + api: 8–16 vCPU, 64 GB RAM, NVMe 1 TB.
* ingestion: 8 vCPU, 32 GB RAM, NVMe 500 GB.

Плюсы: полный контроль и офлайн; самая сильная позиция для SOC2.
Минусы: падение качества генерации vs GPT-4o; заметно более сложная поддержка; 2×GPU.

## 4) Cost-down (под саппорт-кейсы и FAQ) — CPU-only

Когда: бюджет минимальный, вопросы типовые, трафик умеренный.

* LLM: YandexGPT (дешевле) или GPT-3.5-класс.
* Эмбеддинги: CPU-локальные (например, e5-small-v2).
* Векторка: FAISS (CPU) + RDS.
* Переранкер: можно отключить или лёгкая модель на CPU.
* Серверы:all-in-one: 16 vCPU, 64 GB RAM, NVMe 1 TB. Без GPU.

Плюсы: дёшево, просто.
Минусы: ниже качество поиска (без сильного rerank), медленнее индексация больших массивов.


## Итог

Лучший для QuantumForge: Вариант #2 (Hybrid) — локальные эмбеддинги + FAISS(+RDS) + облачный GPT-4o, одна L4 24GB для эмбеддингов и rerank, отдельная CPU-нода под FAISS+API.
Даст: высокое качество поиска/ответа, контроль над данными, умеренную стоимость и простую эксплуатацию на вашем текущем AWS/EKS/RDS.
Масштабирование: горизонтально по подам API, шардированный FAISS по коллекциям (пространства Confluence/домены знаний), при росте до 1–2 млн чанков — перейти на IVF-индексы и добавить вторую CPU-ноду под поисковый слой.
